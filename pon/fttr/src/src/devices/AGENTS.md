# 设备适配代码约定

本文件适用于 `devices/` 及其子目录；同时遵守仓库根目录的 `AGENTS.md`。

## 目录与职责

新增设备遵循「设备注册层 → 厂商适配层 → 型号适配层」：

```text
devices/
├── mod.rs                 # feature 注册、厂商入口分派和公共能力接口
├── generic/               # 与厂商、型号无关的通用 OMCI 桥接
└── star/                  # STAR 厂商入口、型号选择和厂商共用逻辑
    ├── mod.rs
    └── sg631/             # SG631Z-C 专属行为、身份规则及协议差异
        └── mod.rs
```

- 新厂商先建 `devices/<vendor>/mod.rs`，再将具体设备放入
  `devices/<vendor>/<model>/`，例如 `star/sg631/`、`hwtc/v152/`。
- 厂商层负责厂商识别、型号分派和有证据支持的厂商共用逻辑；型号层负责
  该设备的身份关联、实体布局、参数路径及私有行为。
- 顶层注册和控制流程通过厂商入口调用，不跨层直接依赖具体型号模块。
  型号模块尽量限制可见性，由父级对外提供必要接口。
- `generic/` 不得出现厂商或型号的专属判断、串号格式、私有参数路径或补丁。
  型号可以复用通用 OMCI 服务；复用不意味着把专属规则移入 `generic/`。
- 上级 `src/cwmp/` 与核心控制层保留公共机制；新增设备条件放入对应厂商/型号模块，
  通过注册或能力接口接入，不在公共流程继续堆叠型号特判。
- 已有 `hl202/` 为历史布局；不要把它作为新增厂商/型号平铺的模板。
  不为满足目录形式而顺带迁移与当前任务无关的既有设备。

## 编译与能力边界

- 新厂商使用厂商级 Cargo feature，例如 `device-star`；由顶层 `#[cfg]`
  裁剪整个厂商模块。需要型号级裁剪时在厂商层继续细分。
- 同步 `Cargo.toml` 的 `all-devices`、OpenWrt Makefile 的配置项、
  `PKG_CONFIG_DEPENDS` 与 feature 映射，以及能力报告和 README。
- 不因识别到型号或完成身份关联，就宣布支持业务配置。OMCI 桥接、管理引导、
  CWMP 身份关联与业务参数契约分别按实际实现暴露能力。

## 变更验证

- 验证目标厂商 feature 启用和关闭两条路径；关闭后应能编译，且不再应用
  该厂商身份规则。涉及身份关联时检查错误厂商、错误型号、错误串号及多候选歧义。
- 调整分派时回归已有设备，避免扩大匹配范围或改变通用桥接语义。
- 现场操作遵守当前身份、注册代次与资源归属检查；OMCI 回读、真实 GEM 数据、
  管理网络与真实 CWMP RPC 分层验证，不得互相替代。
- 测试和共享记录使用虚构身份或稳定占位符，不写入现场账号、密码或设备标识。
